## 3. Background / Service Worker

**File:** `background.js`

### Script imports (via `importScripts`)
```
xg_shared → xg_parse → xg_timeout → xg_images → xg_settings → xg_prompt → xg_response → xg_reply → xg_adapters → xg_diagnostics → xg_platforms → xg_cooldown → xg_thread → xg_account_memory
```

### Message handlers

| Action | Sender | Description |
|---|---|---|
| `GENERATE_AI_REPLY_WEB` | X content script | Main reply generation pipeline. Queued via `requestQueue` (serial). Calls `handleWebSessionReply()`. |
| `CANCEL_PROVIDER_REQUEST` | X content script | Adds requestId to `cancelledRequests` set; sends cancel to bridge tab |
| `OPEN_PROVIDER_TAB` | popup.js | Opens or activates the dedicated provider tab |
| `REPAIR_X_PAGE` | popup.js | Re-injects all X page scripts + CSS, then triggers rescan |
| `RESCAN_X_PAGE` | popup.js | Sends `DRAFTPULSE_RESCAN` to X tab |
| `CLEAR_VIEW_SNAPSHOTS` | popup.js | Removes snapshot from `chrome.storage.local`; notifies X tab to clear in-memory copy |
| `GET_DIAGNOSTICS` | popup.js | Collects provider statuses, X page status, last request record |

### Request queue
- `requestQueue = Promise.resolve()` — all `GENERATE_AI_REPLY_WEB` requests are serialised via `.then()` chaining.
- `cancelledRequests: Set<string>` — requestIds that should be aborted at next checkpoint.

### Transport layer (`createTransport()`)
Provides the `ProviderAdapter` with four operations:
- `ensureTab(def, opts)` → `getOrCreateDedicatedProviderTab()` — looks up `chrome.storage.session` for tab ID; falls back to querying all tabs by URL pattern; creates new tab if none found.
- `waitReady(def, tabId, timeoutMs)` → `waitForBridge()` — polls `pingProviderBridge()` with 700ms intervals; on first failure, triggers `injectProviderBridge()` (re-inject via `chrome.scripting.executeScript`).
- `send(def, tabId, action, payload, timeoutMs)` → `chrome.tabs.sendMessage()` wrapped in `withTimeout`.
- `cancel(def, tabId, action, requestId)` → same but with 2s timeout.

### Dedicated tab management
- Tab IDs stored in `chrome.storage.session` (keys: `draftpulseProviderTabGemini`, `draftpulseProviderTabChatGPT`, `draftpulseProviderTabDeepSeek`).
- Recovery: if session storage is lost (SW restart), queries `chrome.tabs.query({})` and matches by `urlPattern`, preferring the active/most-recently-accessed tab.

## 4. Gemini Web Session Communication

**File:** `gemini_bridge.js` — injected into `https://gemini.google.com/*`

### Communication pattern
All communication uses `chrome.runtime.onMessage` (bridge listens) and `chrome.tabs.sendMessage` (background sends). Each message includes a `requestId` for correlation and cancellation.

### Message actions handled by bridge

| Action | Description |
|---|---|
| `PING_GEMINI_BRIDGE` | Returns `{ success, ready }` — checks if composer (input box) is found |
| `ATTACH_GEMINI_IMAGE` | Attaches one image file to the composer via file input, paste, or drag-drop |
| `SUBMIT_GEMINI_PROMPT` | Fills composer with prompt text, clicks send button, waits for submission acknowledgement |
| `WAIT_GEMINI_RESPONSE` | Polls response progress — checks if new model response has stabilised |
| `EXTRACT_GEMINI_RESPONSE` | Extracts latest response text, deduplicates, returns reply |
| `CANCEL_GEMINI_WEB` | Marks request as cancelled in the request guard |

### Auto-pipeline (Gemini is `mode: 'auto'`)
1. **Attach images** — `attachGeminiImages()` in background.js loops through images, each sent as `ATTACH_GEMINI_IMAGE`. Bridge tries three strategies: (a) set `<input type="file">` files, (b) dispatch paste event, (c) dispatch drop event. Waits for attachment count to increase. Up to 3 retries per image.
2. **Submit prompt** — `SUBMIT_GEMINI_PROMPT`. Bridge fills composer (textarea: native setter; contenteditable: `execCommand('insertText')` with fallback to `replaceChildren`). Clicks send button. Waits for acknowledgement (user message count increases, or composer text changes, or generating indicator appears). Up to 2 submit attempts.
3. **Poll response** — background.js calls `WAIT_GEMINI_RESPONSE` in a 500ms polling loop. Bridge checks `inspectResponseProgress()`: finds new response via `findNewResponse()` vs baseline, then checks stability via `isResponseStable()` (idle 500ms when not generating, 1500ms while generating).
4. **Extract** — `EXTRACT_GEMINI_RESPONSE`. Bridge extracts text from the last response element, strips thinking/reasoning blocks, deduplicates via `dedupeResponseText()`, ensures it differs from baseline.

### Request guard
`createRequestGuard()` ensures only one active request at a time per bridge page. `tryAcquire()` / `release()` / `cancel()` pattern.

## 5. X DOM Extraction

**File:** `content.js`

### Article scanning
- `scheduleScan()` debounces at 300ms, then iterates `document.querySelectorAll('article[data-testid="tweet"]')`.
- For each article, calls `updateTweet()` which creates or updates a `.draftpulse-panel` toolbar.
- A `MutationObserver` on `document.documentElement` (childList + subtree) triggers rescans on DOM changes.
- Scroll position is preserved: `captureScrollAnchor()` / `restoreScrollAnchor()` prevents jump when panels are inserted.

### Metrics reading (`getMetrics()`)
- **Replies**: `button[data-testid="reply"]` → `aria-label` + `textContent` → `parseMetric()`
- **Reposts**: `button[data-testid="retweet"], button[data-testid="unretweet"]`
- **Likes**: `button[data-testid="like"], button[data-testid="unlike"]`
- **Views**: `a[href$="/analytics"], a[aria-label*="view"]`
- Fallback: scans `div[role="group"]` for buttons/links matching regex patterns (e.g. `/repl|回复|评论/i`)

### Tweet text reading (`readFullTweetText()`)
- Primary: `div[data-testid="tweetText"]` — reads both `innerText` (visible) and `textContent` (full DOM), takes the longer.
- Show-more handling: if `[data-testid="tweet-text-show-more-link"]` is visible, clicks it and polls up to 1600ms for text to expand. This is the **only DOM click** performed by the extension on X pages.

### Tweet identity (`getTweetIdentity()`)
- Extracts `tweetId` from `a[href*="/status/(\d+)"]`
- Extracts `publishedAt` from `time[datetime]` via `Date.parse()`

### Caching
- Tweet meta (image count, identity): cached on panel DOM attribute `data-draftpulse-meta` for 5s
- Metrics: cached on `data-draftpulse-metrics` for 2s (only when views are present)

## 6. Image Extraction

### `getTweetImageDescriptors(article)` (content.js)
1. Queries `div[data-testid="tweetPhoto"] img`, `a[href*="/photo/"] img`, `img[src*="pbs.twimg.com/media/"]`
2. For each `<img>`, calls `classifyImageElement()` → `shouldCollectImage()` which excludes:
   - Images inside video players (`div[data-testid="videoPlayer"]`)
   - Images inside link cards (`[data-testid="card.wrapper"]`)
   - Images inside quote tweets (`[data-testid="tweetQuote"]`)
   - Avatar images (`[data-testid^="UserAvatar"]`, `/profile_images/`)
   - Emoji/icon/logo URLs
3. Calls `pickBestImageSource()` → `pickBestSrcset(srcset)` or falls back to `currentSrc`/`src`
4. If fewer than `MAX_IMAGES(4)` images found, also checks `background-image` CSS on `div[data-testid="tweetPhoto"]` elements

### `collectTweetImages(descriptors, max)` (xg_images.js)
- Filters to `type === 'image'` only
- Normalises URL via `normalizeXImageUrl()` (adds `?name=large`)
- Deduplicates by pathname (`imageIdentityKey`)
- Returns up to `MAX_IMAGES(4)` images

### Constraints
- `MAX_IMAGE_BYTES`: 8 MB per image
- `MAX_TOTAL_IMAGE_BYTES`: 20 MB total
- `MAX_DATA_URL_LENGTH`: 12 MB
- Allowed hosts: `pbs.twimg.com` only
- Allowed MIME types: `image/jpeg`, `image/png`, `image/webp`, `image/gif`

## 7. Reply Generation Flow

Full flow from button click to response:

```
User clicks "生成回复草稿" button
  → content.js: generateReply(article, panel, button)
    → Reads tweet text (readFullTweetText), author, images (getTweetImages)
    → Checks for pending reply (pendingReplies Map) — if exists, fills directly
    → For auto mode (Gemini): checks for open reply editor
    → Generates requestId (crypto.randomUUID)
    → Sends chrome.runtime.sendMessage({ action: 'GENERATE_AI_REPLY_WEB', data: { provider, requestId, tweetText, author, images } })

background.js: handleWebSessionReply(data)
  → Sanitises inputs (sanitizeText, MAX_TWEET_LENGTH=12000)
  → Downloads images (downloadTweetImages) — 2 concurrent workers, fetch with 30s timeout
  → Reads settings from chrome.storage.sync
  → Builds prompt (buildPrompt) with persona, language, emoji, question, disagreement, replyCount
  → Creates ProviderAdapter via createProviderAdapter()
  → adapter.ensureDedicatedTab() — opens/reuses provider tab
  → adapter.waitReady(30s) — polls bridge ping, re-injects on failure
  
  For auto mode (Gemini):
    → adapter.attachImages() —逐张 upload via bridge
    → adapter.submitPrompt() — send prompt to bridge
    → pollForProviderResponse() — 500ms loop calling adapter.waitForResponse()
    → adapter.extractResponse() — get final text
    → normalizeReplyCandidates() — strip prefix, dedupe, split candidates, truncate
    → Returns { mode:'auto', reply, candidates[], imageCount, timings }
  
  For manual mode (ChatGPT/DeepSeek):
    → adapter.prepareRequest() — pre-fill prompt in bridge
    → Activates provider tab
    → Returns { mode:'manual', prepared:true, instruction }

content.js (continued):
  For auto mode:
    → Finds open reply editor (findOpenReplyEditor, polls up to 2500ms)
    → If no editor: stores in pendingReplies, shows toast
    → If editor found: fillXEditor(editor, reply)
    → Shows candidates dropdown if multiple
    → Records last request to chrome.storage.local
  For manual mode:
    → Shows success toast with instruction to copy/paste
```

## 8. Reply Backfill Flow

### `fillXEditor(editor, text)` (content.js)
1. Sanitises reply text via `sanitizeReplyForEditor()` (strips control chars, trims lines)
2. Reads current editor text
3. Calls `decideFill()` (xg_editor.js):
   - **`fill`** — editor is empty → proceed
   - **`skip`** — editor already has identical content (whitespace-normalised comparison) → don't re-insert
   - **`blocked`** — editor has user-written content → refuse to overwrite

### `overwriteXEditor(editor, text)` (content.js)
1. `editor.focus()`
2. Dispatches `beforeinput` event (InputEvent, bubbles, cancelable) so React can sense the incoming change
3. `editor.replaceChildren(document.createTextNode(text))` — direct DOM replacement (avoids `execCommand` which conflicts with React's event system causing double-insertion)
4. Dispatches `input` event to notify React of the change

### Pending replies
- When generation succeeds but no reply editor is open, the reply is stored in `pendingReplies` Map (keyed by tweetId, max 60 entries LRU).
- Next time user clicks the button with the editor open, `tryFillPending()` fills directly without re-generating.

### Candidate switching (`switchCandidate()`)
- When multiple candidates exist (replyCount=3), a dropdown appears.
- Switching verifies the editor still contains the current candidate (whitespace-normalised comparison).
- If editor was modified by user, refuses to switch.
- Otherwise calls `overwriteXEditor()` with the new candidate text.

## 9. Snapshot Storage

### Storage key
- `chrome.storage.local` key: `draftpulseViewSnapshotsV1` (defined as `SNAPSHOT_STORAGE_KEY` in xg_growth.js)

### Snapshot structure
```js
{
  tweetId: string,      // numeric tweet ID
  views: number,        // rounded view count
  observedAt: number,   // Date.now() timestamp
  publishedAt: number   // tweet publish timestamp
}
```

### In-memory store
- `viewSnapshots` object in content.js, keyed by tweetId.
- Loaded at startup from `chrome.storage.local`, normalised via `normalizeSnapshotStore()` (migrates legacy formats).

### `schedulePersistSnapshots()` (content.js)
- Debounced write: 1200ms delay after last change.
- Maximum delay guard: 5000ms — if continuous scans keep resetting the debounce, forces a write after 5s.
- Epoch-based invalidation: `snapshotEpoch` counter; when snapshots are cleared, epoch increments, causing any in-flight persist to be discarded.
- Before writing, calls `pruneSnapshotStore()`.

### Pruning (`pruneSnapshotStore()` in xg_growth.js)
- Removes entries older than 14 days (`SNAPSHOT_MAX_AGE_MS`)
- Keeps at most 600 entries (`SNAPSHOT_MAX_ENTRIES`)
- Sorts by `observedAt` descending before slicing

## 10. View Growth Calculation

**File:** `shared/xg_growth.js` — `computeViewGrowth(input)`

### Input
```js
{ tweetId, publishedAt, views, now, snapshot, minIntervalMs, minAgeMs }
```

### Output
```js
{ available, source, rate, averageRate, ageHours, intervalMinutes, snapshot }
```

### Source determination (decision tree)

1. **`unavailable`** — No valid tweetId, publishedAt, or views. Returns immediately.
2. **`fresh`** — Tweet age < 1 minute (`MIN_AGE_FOR_RATE_MS`). Rate is `null`; snapshot is recorded but no rate shown. Prevents absurdly large numbers from very new tweets.
3. **`average`** — No previous snapshot, or elapsed time since last snapshot < 3 minutes (`SNAPSHOT_MIN_INTERVAL_MS`). Rate = `views / ageHours` (simple average).
4. **`observed`** — Previous snapshot exists and interval ≥ 3 minutes. Rate = `(currentViews - snapshotViews) / elapsedHours`. This is the actual observed growth rate.

### Edge cases
- **Future publish date**: If `publishedAt > now + 5min`, returns unavailable (clock skew guard).
- **View count decrease**: Falls back to `average` rate; preserves old `views` baseline in snapshot (only refreshes `observedAt`). Prevents negative rates.
- **Minimum age clamp**: `ageHours` is clamped to minimum `1/60` (1 minute) to avoid division by zero.
- **Rate formatting**: ≥10000 → `viral` (🔥); ≥1000 → `fast` (⚡); else `normal` (📈).

## Safety Confirmation

**DraftPulse v2.0 is a read-and-draft tool. It never performs social actions on X on the user's behalf.**

- ✅ **No auto-posting** — The extension never clicks "Post", "Tweet", or "Reply Send" on X.
- ✅ **No auto-like** — The extension never clicks the Like button.
- ✅ **No auto-follow** — The extension never clicks any Follow button.
- ✅ **No auto-repost** — The extension never clicks the Repost/Retweet button.
- ✅ **No auto-reply-send** — The extension fills the reply editor with draft text but never submits it. The user must manually review and click Send.
- ✅ **The only DOM click on X pages is `showMore.click()`** for expanding truncated tweets. All other clicks (send, attach) happen exclusively in the dedicated provider tabs (Gemini/ChatGPT/DeepSeek).
